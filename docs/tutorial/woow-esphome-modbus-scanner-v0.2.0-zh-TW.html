完整實作指南

從零理解 Modbus 位址掃描生命週期

本文件說明 Home Assistant 自訂整合 Woow ESPHome Modbus Scanner 0.2.0 的安裝、六個動作、固定模擬資料與安全邊界。你可用它設計儀表板、自動化與 API 用戶端，但不可把模擬結果當成現場設備資料。

所有章節均顯示；停用 JavaScript 也能閱讀全部內容。

列印版本：Woow ESPHome Modbus Scanner v0.2.0 繁體中文完整教學。

1. 版本範圍、目的與非目標

先確認：0.2.0 只有可重現的 MockGatewayProvider。選取 esphome_device_id 也不會接觸該裝置；本版沒有 ESPHome adapter、沒有實體 RS-485 I/O，也不是韌體。

適合做

  • 練習 Home Assistant 動作回應與 response_variable。
  • 開發掃描 UI、REST 用戶端與自動化。
  • 驗證 running、completed、cancelled、failed 生命週期。
  • 理解 timeout、例外、碰撞與閘道中斷的語意。

不會做

  • 不偵測、設定或變更實體 Slave ID。
  • 不保證找到所有節點或識別唯一實體設備。
  • 不寫暫存器、不重啟節點、不代理 ESPHome API。
  • 不跨 Home Assistant 重載或重啟保存歷史。

「掃描」在本版是針對固定 fixture 執行真實的協調器流程，而不是虛構同步回傳。這讓用戶端可在無硬體下正確處理非同步工作、取消、錯誤與結果格式。

2. 為何分離 provider 與 coordinator

Provider 擁有閘道與傳輸知識：列出能力、依序探測、逐筆發出正規化 ProbeResult、回報傳輸失敗並合作式取消。Coordinator 則是信任邊界：驗證請求及 provider 輸出、產生 UUID、管理任務、同一閘道互斥、統計、歷史及公開 JSON。分離後，未來 adapter 不得繞過既有安全與結果語意。

Home Assistant 動作生命週期

  1. 安裝並建立唯一 config entry；六個動作才可用。
  2. start_scan 或 test_address 驗證資料，先保留 provider/gateway 所有權，再建立非 eager 背景 task，立即回傳初始 status 與 canonical UUID scan_id。
  3. provider 按位址輸出結果；coordinator 再驗證位址、型別、重複、延遲、例外碼及 identity。
  4. get_scan_status 輪詢進度；get_scan_results 可隨時取目前快照。
  5. cancel_scan 設定合作式取消旗標；在目前交易後、下一筆交易前生效。整合卸載則硬取消並等待清理。
  6. 終態進入記憶體歷史；預設只保留最近 20 筆終態掃描。
Home Assistant 現代文件稱 service call 為「執行動作」。YAML 使用 action:；舊式 service: 語法仍常見，但本教學以目前的 action 語彙與格式為主。

3. Modbus 位址與發現限制

  • Modbus Serial Line 規範的個別 server/slave 位址為 1–247。本整合據此只接受此範圍。
  • 位址 0 是 broadcast，不是可輪詢的個別節點；server 不對 broadcast 回覆，因此掃描禁止 0。
  • Modbus 沒有能保證列出所有設備的通用 discovery。每個裝置是否支援某功能碼、資料模型與 timing 取決於產品文件。
  • 功能碼 43/14 (0x2B/0x0E) 的 Read Device Identification 是選用能力；無回覆不等於沒有設備。
  • CRC 有效的 Modbus exception 表示該位址有 responder，只是拒絕功能或資料；例如 mock 的 code 2 為 Illegal Data Address、code 3 為 Illegal Data Value。
  • 同一 RS-485 線上若有重複 ID，回覆可能重疊、CRC/framing 不一致；也可能只是終端、偏壓、雜訊或 timing 問題。因此只能標為 possible_collision，不能宣稱唯一設備。
  • timeout 可能來自離線、不支援探測、baud/parity 不符、線路、閘道、回應較慢或當下忙碌；它不證明位址未使用。

未來實體掃描即使全是 read-only，也會增加匯流排流量，可能和正常輪詢競爭。timeout_ms、retries 與 inter_request_delay_ms 是上限內的節奏控制；最壞估算為 位址數 × timeout_ms × (retries + 1) + (位址數 − 1) × delay。0.2.0 mock 不實際套用 timeout/retry 傳輸，但 status 仍回傳此估算；mock 位址間延遲取內建 10 ms 與要求 delay 的較大值。

4. 安裝、建立整合與驗證

HACS 自訂儲存庫

  1. HACS → Integrations → 右上選單 → Custom repositories。
  2. 填入 https://github.com/WOOWTECH/Woow_ha_esphome_modbus_scanner，類別選 Integration。
  3. 下載 Woow ESPHome Modbus Scanner，重新啟動 Home Assistant。
  4. 設定 → 裝置與服務 → 新增整合，搜尋名稱並建立一次。設定流程是 singleton，第二筆會被拒絕。

手動安裝

  1. 下載 v0.2.0 source archive，將其中 custom_components/woow_esphome_modbus_scanner/ 完整複製到 HA 設定目錄同名路徑。
  2. 確認至少有 manifest.json、services.yaml、Python 模組與 translations，然後重新啟動。
  3. 由設定 → 裝置與服務新增整合。

Modbus Scanner 側邊欄

  1. 建立 config entry 後，在左側選 Modbus Scanner（雷達圖示）；直接路徑是 /woow-esphome-modbus-scanner，所有 HA 使用者皆可見。
  2. 按 Refresh gateways，確認模擬 gateway；ESPHome selector 在 0.2.0 明確停用，因為沒有實體 provider。
  3. Basic 欄位填含頭尾 Slave ID 1–247、單址測試位址與六個 mock quick profiles；Advanced 欄位提供 probe type、register 0–65535、count 1–125、timeout 10–10000 ms、retry 0–5、delay 0–5000 ms 與 pause flag。
  4. 勾選 best-effort 警告後 Start scan；畫面以每秒一次且不重疊的呼叫輪詢，completed／cancelled／failed 終態自動載入 results。也可手動 Refresh status/results、Cancel 或 Test address。
  5. 解讀進度、六種 outcome counts 與可排序 responder 證據表。timeout 只計數；每個 outcome 的可能原因與疑難排解都在頁底。
  6. 偏好、展開狀態、最近 scan ID 只存瀏覽器 localStorage；不保存 token、host、frame、憑證或回應。HA 重載後舊 ID 可能因記憶體歷史消失而 unknown。
權限風險：側邊欄與六服務永久開放給所有已驗證 HA 使用者。未來實體 provider 可能讓任何帳號影響匯流排；啟用硬體前必須重新做威脅評估。

最小驗證

開啟開發者工具 → 動作，執行 woow_esphome_modbus_scanner.list_gateways，要求顯示回應。應只看到 mock:rs485-gateway、simulated: true 與六種 profiles。若動作不存在，先檢查 config entry 是否載入與日誌。

5. 六個公開動作與全部欄位

Domain 固定為 woow_esphome_modbus_scanner。公開動作只有以下六個。

list_gateways

無欄位，必定要求回應；列出 provider 擁有的閘道與能力。mock 效果是回傳唯一模擬閘道。未來意圖是由每個 adapter 誠實列出可用閘道，而非把 HA device registry 當傳輸。

start_scan 欄位

start_scan 完整資料欄位、預設值、範圍與行為

provider選用；mock僅 mock選定模擬 provider；未來識別 adapter。
gateway_id選用；mock:rs485-gateway非空字串，但須是 provider 列出者選唯一 fixture；未來精確選 transport/gateway。
esphome_device_id選用；無字串，UI selector 篩 ESPHome 整合裝置接受但完全忽略、不接觸裝置；為未來映射保留。
start_id必要；UI 預填 1整數 1–247含首位址；必須 ≤ end_id。
end_id必要；UI 預填 12整數 1–247含末位址。
probe_type選用；device_identificationdevice_identification、holding_register、input_registerfixture outcome 不隨 probe 改變；未來只允許這三種唯讀探測。
register_address選用；0整數 0–65535mock 不改結果；未來僅 register probes 使用的 zero-based 位址。
register_count選用；1整數 1–125mock 不改結果；未來為讀取數量。

retries選用；1整數 0–5mock 不重試；用於最壞估算，未來表示首次後額外嘗試。
inter_request_delay_ms選用；100整數 0–5000 msmock 位址間至少 10 ms；未來是交易間最小延遲。
pause_normal_polling選用；false布林mock 無輪詢、無硬體副作用；未來僅 adapter 明確支援才可暫停並在 finally 恢復。

6. 完整 UI 與自動化實作

在開發者工具 → 動作選擇對應 action，切至 YAML 可貼入以下內容。「回應」動作需要勾選／要求 response；腳本與自動化使用 response_variable 保存回傳。

Lab A：列出閘道

action: woow_esphome_modbus_scanner.list_gateways
response_variable: gateway_reply

預期 gateway_reply.gateways[0].simulated 為 true；它不是連線狀態證明。

Lab B：啟動範圍掃描

action: woow_esphome_modbus_scanner.start_scan
data:
  provider: mock
  gateway_id: mock:rs485-gateway
  start_id: 1
  end_id: 12
  probe_type: device_identification
  register_address: 0
  register_count: 1
  timeout_ms: 500
  retries: 1
  inter_request_delay_ms: 100
  pause_normal_polling: false
  mock_profile: found_default
  safety_confirmed: true
response_variable: started

Lab C：查狀態與結果

- action: woow_esphome_modbus_scanner.get_scan_status
  data:
    scan_id: "{{ started.scan_id }}"
  response_variable: snapshot
- wait_template: "{{ snapshot.status != 'running' }}"
  timeout: "00:00:05"
  continue_on_timeout: true
- action: woow_esphome_modbus_scanner.get_scan_results
  data:
    scan_id: "{{ started.scan_id }}"
  response_variable: result
自動化修正：上例只示範兩個查詢，wait_template 不會自行更新 snapshot。實務上用 repeat 每次重呼 status；勿建立無延遲的 busy loop。

Lab D：可用的輪詢自動化

alias: Mock Modbus 掃描並等待
mode: single
sequence:
  - action: woow_esphome_modbus_scanner.start_scan
    data:
      start_id: 1
      end_id: 12
      inter_request_delay_ms: 100
      mock_profile: found_default
      safety_confirmed: true
    response_variable: started
  - repeat:
      sequence:
        - delay: "00:00:01"
        - action: woow_esphome_modbus_scanner.get_scan_status
          data:
            scan_id: "{{ started.scan_id }}"
          response_variable: snapshot
      until:
        - condition: template
          value_template: "{{ snapshot.status != 'running' }}"
  - action: woow_esphome_modbus_scanner.get_scan_results
    data:
      scan_id: "{{ started.scan_id }}"
    response_variable: result
  - action: persistent_notification.create
    data:
      title: Mock Modbus 掃描完成
      message: >-
        狀態 {{ result.status }}；回應者
        {{ result.responders | count }}；逾時
        {{ result.outcome_counts.timeout }}

Lab E：取消

action: woow_esphome_modbus_scanner.cancel_scan
data:
  scan_id: "00000000-0000-0000-0000-000000000000"
response_variable: cancelled

換成 start 回傳的 UUID。取消是合作式；回傳時可能仍 running 且 cancellation_requested: true，稍後再查才會是 cancelled。短掃描也可能已 completed。

Lab F：單址測試

action: woow_esphome_modbus_scanner.test_address
data:
  address: 7
  probe_type: device_identification
  mock_profile: possible_collision
response_variable: tested

它仍是背景 scan，回傳 scan_id；再用 status/results 讀取，不是同步的單筆 probe 回應。

7. 精確回傳 payload 與狀態解讀

list_gateways

{"gateways":[{"provider":"mock","gateway_id":"mock:rs485-gateway",
"name":"Simulated RS-485 Gateway",
"capabilities":["device_identification","holding_register","input_register","cancellation"],

Status 欄位

start_scan、test_address、get_scan_status 與 cancel_scan 的 status snapshot
欄位精確意義
scan_id隨機 canonical lowercase hyphenated UUID；當作不透明識別碼。
provider / gateway_id請求的並行鍵。
status / phase目前完全相同，值為 running、completed、cancelled、failed。
current_address尚未產生結果前 null；之後為最近完成或失敗的位址，不是「下一個」。
completed_addresses / total_addresses已記錄 outcome 數與含首尾的要求總數；取消／失敗時可小於總數。
progress_percentcompleted ÷ total × 100，四捨五入一位。
responder_countidentified + responded + modbus_exception + possible_collision；不含 timeout/gateway_error。
outcome_counts六種 outcome 永遠都有整數 key，即使為 0。
started_at / finished_atUTC ISO 8601；running 時 finished_at 為 null。
estimated_worst_case_ms由要求 timing 公式計算的保守值，不是 ETA，也不是 mock 實際時間。
cancellation_requested是否已要求合作式取消；不是已取消保證。
errorfailed 的文字原因；其他通常 null，勿解析文字做程式邏輯。

Results 欄位與 outcome

Results 重複 scan/provider/gateway/status/phase，另含 responders、counts、completed/total、固定 best_effort: true、固定 uniqueness_guaranteed: false 及 error。responders 只保留 responder evidence；gateway_error 雖在內部保留，因不是 responder 而不出現在公開 responders。timeout 只統計、不保留明細。

六種 ScanOutcome 的判讀
outcome是否 responder解讀
identified是有效 device-identification，明細另有全字串 identity；不保證實體唯一。
responded是有效一般 Modbus 回應，沒有 identity。
modbus_exception是CRC-valid 協定例外；含 0–255 exception_code。
timeout否未收到有效回覆；只計數，不證明空位址。
possible_collision是（模糊證據）可能重複 ID 或匯流排雜訊，不得當唯一節點。
gateway_error否傳輸無法繼續；scan 為 failed，error 有文字，counts 增加一次。

每筆 responder 固定有 address、outcome、非負整數 latency_ms、detail；例外才有 exception_code，識別成功才有 identity。

9. 全使用者政策、安全、UUID、歷史與並行

永久全使用者政策

六個動作與 Modbus Scanner 側邊欄不做 admin/user 權限檢查；每位已驗證 HA 使用者都可操作。這是明確產品決策，不是暫時例外。未來若加入實體 provider，任一使用者可能產生匯流排流量、干擾正常輪詢或看到 responder 證據；安裝者必須管控帳號並在啟用硬體前重新評估風險。

安全確認

範圍掃描只接受真正 boolean true。這個確認不讓掃描變得無風險，也不證明設備不存在／唯一。test_address 僅隱含單址範圍確認。

UUID 與未知掃描

查詢／取消只接受 canonical 小寫連字號 UUID，例如 53f04d1e-6a3b-4ab9-98d6-8e224677bdef。格式正確但已淘汰或重載前的 ID 會回 Unknown Modbus scan ID。

歷史

預設保留最近 20 筆終態於 RAM。第 21 筆終態會淘汰最舊者；重載、卸載、重啟不持久化。不要把它當稽核資料庫。

並行與競態

同一 (provider, gateway_id) 同時只准一個 scan，範圍掃描和單址測試彼此也衝突；第二個呼叫得到 busy 錯誤及 active scan ID。不同 gateway 理論上可並行，但 0.2.0 只有一個。所有權在排程前建立，在 completion/failure/cancellation 的 finally 釋放。卸載會讓舊 generation fail closed，取消並等待任務，避免服務重新註冊競態。

10. REST API 範例與 token 安全

Home Assistant REST 服務端點是 POST /api/services/<domain>/<service>?return_response。會回應的動作使用 return_response；實際 envelope 由 HA API 版本決定，動作資料通常位於回應的 service_response。以下只呼叫 mock。

export HA_URL='https://homeassistant.example'
read -rsp 'Home Assistant token: ' HA_TOKEN; printf '\n'

curl --fail-with-body -sS \
  -H "Authorization: Bearer ${HA_TOKEN}" \
  -H 'Content-Type: application/json' \
  -X POST "${HA_URL}/api/services/woow_esphome_modbus_scanner/start_scan?return_response" \
  --data '{
    "provider":"mock",
    "gateway_id":"mock:rs485-gateway",
    "start_id":1,
    "end_id":12,
    "mock_profile":"found_default",
    "safety_confirmed":true
  }'

取出回傳的 scan_id 後：

SCAN_ID='以回傳 UUID 取代'
curl --fail-with-body -sS \
  -H "Authorization: Bearer ${HA_TOKEN}" \
  -H 'Content-Type: application/json' \
  -X POST "${HA_URL}/api/services/woow_esphome_modbus_scanner/get_scan_status?return_response" \
  --data "{\"scan_id\":\"${SCAN_ID}\"}"
Token 是完整帳戶憑證。只用 HTTPS（明確受控的 loopback 開發除外）；不要放進 HTML、YAML repo、shell history、URL query、截圖或日誌。用環境變數／secret store，限制檔案權限，測試後 unset HA_TOKEN；若洩漏立即撤銷。任何使用者 token 都是高風險帳戶憑證；全使用者政策不降低 token 洩漏風險。

12. 未來 ESPHome adapter 路線圖，不是現況承諾

本節是必要條件與方向，不是已支援聲明。ESPHome device selector 只證明 HA 能選到 registry 裝置，不證明有低階 serial/Modbus transaction API。
  1. 先確認受支援的 ESPHome／Home Assistant 上游 API，撰寫 ADR 與版本變更；不能依賴私有不穩定介面後宣稱支援。
  2. 把 esphome_device_id 明確解析成 provider gateway，驗證可用性與能力。
  3. 只執行 device identification、holding/input register read；不得寫 register、改 Slave ID、重啟節點。
  4. 沿用 coordinator 驗證、UUID、歷史、回傳格式和每 gateway 單工；adapter 不隱藏平行要求。
  5. 正確落實 timeout、額外 retries、交易間 delay 與 inclusive 範圍。
  6. 若支援 pause_normal_polling，只暫停選定 gateway，並在成功、失敗、取消、卸載的 finally 恢復；不支援就明確拒絕。
  7. 交易間檢查取消；清理 transport 後讓 task cancellation 傳遞。
  8. 區分 CRC-valid exception、timeout、transport loss、ambiguous framing；不能把 collision 當唯一發現。
  9. 公開 response/log 不洩露 credential、host、raw frame 或私有 registry 資料。
  10. 加入選定上游 API 的 integration tests、實體安全矩陣與文件，再發布新版本。
